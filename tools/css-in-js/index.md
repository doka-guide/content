## Кратко

**CSS-in-JS** — это подход, при котором стили пишут прямо в JavaScript-коде компонентов, а не в отдельных CSS-файлах. Это позволяет использовать возможности JavaScript для динамического управления стилями и обеспечивает изоляцию стилей на уровне компонентов, предотвращая конфликты и облегчая поддержку кода.

Существуют разные решения CSS-in-JS, но их объединяет общий принцип: стили описывают в JavaScript-коде. Это может быть объект, [теговый шаблон](/js/template-strings/#tegovyy-shablon) или вызов специальной функции.

Библиотека превращает такие описания в CSS и привязывает стили к компоненту через уникальный идентификатор. Чаще всего это автоматически созданный класс. Например, вместо общего класса `.button` появится `.acz123_button` или `.Component-button-aXyZ`.

Самые известные библиотеки CSS-in-JS — [Styled Components](https://styled-components.com/) и [Emotion](https://emotion.sh/docs/introduction). Emotion почти не развивается, а Styled Components с 2025 года в режиме поддержки. Активнее развиваются библиотеки, которые готовят стили заранее, при сборке: [vanilla-extract](https://vanilla-extract.style/), [Panda CSS](https://panda-css.com) и [StyleX](https://stylexjs.com).

## Почему CSS-in-JS?

Главное преимущество CSS-in-JS — возможность использовать конструкции JavaScript при описании стилей компонента. В зависимости от проекта это может помочь описывать динамические стили, которые зависят от условий, а также упростить работу с темами.

<aside>

☝️ CSS-in-JS не универсальное решение

Изоляцию стилей и управление темами можно сделать с помощью обычного CSS, [препроцессоров](/tools/preprocessors/) или CSS Modules. Сам CSS за последние годы закрыл часть проблем, ради которых придумали CSS-in-JS. В нём появились:

- вложенность;
- [каскадные слои `@layer`](/css/layer/) для управления порядком правил;
- [`@scope`](/css/scope/) для изоляции стилей;
- [кастомные свойства](/css/var/), или CSS-переменные, для общих констант, тем и стилей, которые меняются на лету.

Выбор подхода зависит от специфики проекта и предпочтений команды.

</aside>

## Краткая история

Бегло рассмотрим историю появления решений CSS-in-JS.

<aside>

🏃‍♂️ Коротко, если нет времени читать всё

CSS зародился в 90-е годы и долго справлялся с задачами веб-разработки, потому что был простым. Однако с появлением [реактивных фреймворков](/tools/reactivity/) и переходом к большим одностраничным приложениям (_SPA_) стало видно, что стили плохо масштабируются. С 2014 года разработчики начали экспериментировать с подходом CSS-in-JS, так появились библиотеки вроде [JSS](https://cssinjs.org/).

</aside>

### Становление CSS

CSS (каскадные таблицы стилей) появился в 90-е годы. В 1996 году консорциум [W3C](https://www.w3.org/) выпустил первую рекомендацию CSS, и язык стал стандартным способом описывать вид веб-документа. Он был достаточно мощным для проектов тех лет и достаточно простым, чтобы все желающие могли быстро начать работу.

### Появление реактивных фреймворков и SPA

До 2010-х годов разработчики в основном делали многостраничные приложения с чётким разделением ответственности:

- HTML определял разметку страницы;
- CSS описывал, как она будет выглядеть;
- JavaScript отвечал за интерактивность.

С течением времени развивался не только CSS, но и JavaScript. Появилась новая экосистема разработки и реактивные фреймворки: AngularJS (2010), React (2013), Vue.js (2014). Разработчики начали переходить от многостраничных приложений к одностраничным (SPA), а пользователи стали ожидать от них более динамичного и сложного поведения.

### Кристофер Шедо, его доклад о проблемах CSS и разработка первых решений CSS-in-JS

В 2014 году Кристофер Шедо (инженер Facebook) [выступает с докладом](https://speakerdeck.com/vjeux/react-css-in-js) о семи проблемах CSS, которые нужно решить для беспроблемной разработки больших динамичных приложений:

1. **Глобальное пространство имён**
Все CSS-селекторы живут в одной глобальной области, из-за чего стили разных компонентов могут конфликтовать или перезаписывать друг друга.

1. **Зависимости**
Компонент может забыть подключить свой CSS, и это незаметно: страница работает, потому что тот же файл уже подключил другой компонент. Если убрать другой компонент, стили пропадут.

1. **Удаление неиспользуемого кода**
В больших проектах часто копится CSS, который больше нигде не применяется, и его непросто безопасно убрать: неясно, где он ещё нужен.

1. **Минификация**
Длинные имена классов раздувают и CSS, и HTML. Если классы создаёт функция, их имена можно автоматически сократить, и код станет меньше.

1. **Общий доступ к константам**
Одни и те же значения, например цвета и размеры, нужны и в CSS, и в JavaScript. Хранить их в одном месте и использовать в обоих языках сложно.

1. **Проблемы каскада**
Когда несколько правил стилизуют одни и те же элементы, порядок подключения CSS может приводить к непредсказуемым результатам и конфликтам.

1. **Изоляция**
Нужен способ гарантировать, что стили компонента не заденут другие компоненты. Особенно это важно в больших проектах.

В этом же году начинается работа над CSS-in-JS. Первые экспериментальные решения появились вокруг React. Одной из первых полноценных реализаций «CSS в JavaScript» часто называют [JSS](https://cssinjs.org/), хотя сама библиотека не привязана к фреймворку.

## Runtime и zero-runtime

За время развития CSS-in-JS появилось много вариантов реализации. Одни создают стили прямо в браузере пользователя (runtime). Другие переносят почти всю работу на этап сборки (zero-runtime). Ниже разберём особенности обоих подходов.

<aside>

💡 Примеры работы библиотек

Библиотека [Styled Components](https://styled-components.com/) собирает стили и вставляет их в [`<style>`](/html/style/) прямо во время работы приложения (**runtime**).

Например, библиотека [vanilla-extract](https://vanilla-extract.style/) обрабатывает файлы стилей на TypeScript или JavaScript во время сборки приложения (**zero-runtime**). В результате получаются обычные статические CSS-файлы. Страница подключает их как любые другие стили. Браузеру не нужно выполнять JavaScript, чтобы создать или применить эти стили.

</aside>

### Runtime-подход

#### Суть подхода

Библиотека создаёт стили и добавляет их в [DOM](/js/dom/) во время выполнения приложения, в рантайме. При рендере или смене состояния она создаёт или обновляет теги `<style>` и классы.

#### Плюсы

- Легко менять стили на лету в зависимости от состояния, темы и так далее.
- Удобно изолировать логику стилизации в самих компонентах, сохраняя стиль и логику рядом.

#### Минусы

- Дополнительная нагрузка в рантайме: при каждом рендере библиотека может создавать и вставлять новые стили, а это замедляет страницу.
- Возможны сложности и повышенные требования к настройке серверного рендеринга (_SSR_) и кеширования стилей.
- Сложности с серверными компонентами React (React Server Components). Runtime-библиотеки передают тему и вставляют стили через контекст и хуки, а в серверных компонентах их нет. Emotion в серверных компонентах не работает, поэтому компоненты со стилями приходится делать клиентскими.

#### Библиотеки, реализующие подход

- [Styled Components](https://styled-components.com/)
Стили описывают в теговых шаблонах внутри JavaScript или TypeScript. В рантайме библиотека создаёт уникальные классы и вставляет стили в DOM. С 2025 года в режиме поддержки, но обновления выходят. В версии 6.3 (январь 2026 года) появилась поддержка серверных компонентов React, темы в них делают через CSS-переменные.
- [Emotion](https://emotion.sh/docs/styled)
Тоже создаёт стили в рантайме. Стили можно писать и теговыми шаблонами, и объектами, через `styled` или `css`. Новые версии выходят редко, последняя — в 2025 году.
- [JSS](https://cssinjs.org/)
Стили описывают JavaScript-объектами, а библиотека превращает их в CSS в рантайме. Находится в режиме поддержки: выходят только исправления безопасности и критических ошибок, новых возможностей не будет.

### Zero-runtime-подход

#### Суть подхода

Библиотека вычисляет стили на этапе сборки и выносит их в CSS-файлы. В результате в браузер попадает статический (или почти статический) CSS, а логика генерации стилей не исполняется или почти не исполняется.

#### Плюсы

- Нет накладных расходов в браузере (минимальный дополнительный JS-код).
- Поэтому обычно выше производительность и лучше метрики загрузки.
- Проще реализовать серверный рендеринг, так как стили уже готовы к моменту, когда HTML отдаётся клиенту.

#### Минусы

- Ограничения в динамических стилях: большая часть логики должна быть статически рассчитана во время сборки, поэтому зависимые от состояний стили могут быть менее гибкими.
- Сложная сборка: обычно нужно дополнительно настроить сборщик ([Webpack](/tools/webpack/), Vite и другие).

#### Библиотеки, реализующие подход

- [Linaria](https://linaria.dev/)
Анализирует CSS, написанный в теговых шаблонах, на этапе сборки и извлекает его в отдельные файлы. В рантайме остаются классы и небольшой код, который задаёт CSS-переменные для стилей, зависящих от пропсов, то есть параметров компонента.
- [vanilla-extract](https://vanilla-extract.style/)
Стили пишут на TypeScript или JavaScript, а при сборке библиотека превращает их в обычные CSS-файлы. На клиенте JavaScript для стилей почти не нужен.
- [Panda CSS](https://panda-css.com)
Стили описывают объектами в JavaScript/TypeScript, а при сборке библиотека превращает их в атомарные CSS-классы: один класс — одно объявление.
- [StyleX](https://stylexjs.com)
Библиотека от Meta, компании-владельца Facebook. Тоже превращает стили в атомарный CSS при сборке, на ней сделаны интерфейсы Facebook и Instagram.

<aside>

🤓 Режим ботаника

Runtime и zero-runtime — два полюса. Многие библиотеки работают между ними: генерируют стили при сборке, но оставляют в рантайме немного кода для CSS-переменных или особых динамических стилей, как Linaria. В этой статье мы разбираем только два полюса, чтобы не усложнять тему.

</aside>

## Основы синтаксиса

Во многих библиотеках стили пишут в теговых шаблонах, например в Styled Components и Emotion. Разберём этот синтаксис на примере Styled Components. В vanilla-extract, Panda CSS и StyleX стили описывают объектами, но идея та же. За подробностями загляните в документацию к конкретной библиотеке.

### Простейший компонент

Опишем кнопку со стилями прямо в JavaScript-коде. Функция `styled('button')` создаёт компонент, который работает как обычный [`<button>`](/html/button/), но с нашими стилями.

```javascript
import styled from 'styled-components'

const Button = styled('button')`
  color: white;
  background-color: black;
  border: none;
`

export default Button
```

### Динамические стили

Ниже показана функция из файла _utils.js_, которая генерирует динамические стили для фона в зависимости от флага `isPrimary`. При `true` фон синий, а при наведении тёмно-синий. При `false` фон серый и тёмно-серый.

```javascript
import {css} from 'styled-components'

function getBackgroundColor(isPrimary) {
  return css`
    background-color: ${isPrimary ? 'blue' : 'gray'};

    &:hover {
      background-color: ${isPrimary ? 'darkblue' : 'dimgray'};
    }
  `
}

export {getBackgroundColor}
```

Вызовем `getBackgroundColor(true)` внутри шаблона стилей компонента `Button`. Компонент получит готовый блок стилей из функции. Это удобно, если цвета фона нужны в разных компонентах, а описать их хочется в одном месте.

```javascript
import styled from 'styled-components'
import {getBackgroundColor} from './utils.js'

const Button = styled('button')`
  color: white;
  border: none;
  ${getBackgroundColor(true)};
`

export default Button
```

Такая вставка блока стилей работает в runtime-библиотеках вроде Styled Components и Emotion. Zero-runtime-библиотеки готовят стили при сборке, поэтому динамику из пропсов там обычно делают через CSS-переменные или заранее описанные варианты стилей.
