## Кратко

Каждая программа со временем становится большой. Чем больше в проекте кода, тем сложнее в нём ориентироваться, писать и поддерживать.

Модули помогают организовать код так, чтобы с проектом было проще и удобнее работать, позволяют переиспользовать код и структурировать программу.

## Как понять

_Модуль_ — обособленная часть системы. Обычно один модуль — это один файл. Модули можно воспринимать как части конструктора, из которых собирается программа.

В модуле по умолчанию всё скрыто. Наружу модуль отдаёт только то, что разработчики решили открыть. Это _экспорты_. Эту функциональность можно _импортировать_ в других модулях и использовать.

Таким образом, модуль — это чёрный ящик с одним входом (импорт) и одним выходом (экспорт), через которые этот модуль «общается» с другими.

Модули можно сравнить с функциями: они решают те же проблемы, но в более крупном масштабе. Функции помогают разбивать большую задачу на мелкие, а модули — разбивать большой проект на мелкие части. Функции помогают структурировать архитектуру решения конкретной задачи, а модули — проекта целиком.

### Польза модулей

Идея и польза модулей в первую очередь в том, что они помогают справляться со сложностью программы. Если мы работаем с проектом на 20 тысяч строк, будет совершенно неудобно хранить весь код в одном файле.

|  | Без модулей | С модулями |
| --- | --- | --- |
| Навигация и перемещение по проекту | Сложно. Чтобы поработать над двумя частями кода, придётся или открывать файл дважды, или прыгать между секциями файла. | Просто. Модули можно открыть параллельно и работать над ними одновременно. |
| Охват проекта целиком | Сложно, зачастую невозможно. Простыня на несколько десятков экранов не даст понять, как проект устроен, оценить его структуру и взаимосвязи между частями программы. | Сильно проще. Структура папок и файлов проекта, построенного на модулях, помогает охватить структуру и понять, как проект устроен. |
| Повторное использование кода | Затруднено, иногда вовсе исключено. Чтобы переиспользовать код из такой портянки, его нужно отделить, почистить от лишних зависимостей, проверить его работу отдельно и встроить в новый проект. Иногда проще написать всё с нуля. | Просто. Модули можно использовать в нескольких проектах. |

### Модули в JavaScript

Изначально модулей в JavaScript не существовало. Считалось, что скрипты, подключаемые к страницам, очень простые, и модульная система не нужна.

Время шло, приложения на JavaScript становились всё сложнее, и стало ясно, что без модулей не обойтись. Тогда появились первые попытки «принести» модули в JavaScript.

Сейчас модули уже появились и поддерживаются, но их «становление» проходило медленно. Модульных систем было несколько: AMD, CommonJS, UMD и ES-модули.

Современной системой считаются ES-модули. AMD и UMD сейчас почти не используют, а на CommonJS до сих пор написано много кода для Node.js. Если вас интересуют легаси-системы, загляните в подраздел «Модульные системы, которые использовались до ES-модулей». Если нет, смело его пропускайте.

<details>
  <summary>Модульные системы, которые использовались до ES-модулей</summary>

_AMD (asynchronous module definition)_ — асинхронное определение модулей, одна из первых попыток создать систему модулей.

Её изначально реализовали в библиотеке Require.js. Модули определяли функцией `define`, и выглядело это довольно многословно. Модуль мог вернуть объект с данными или функцию. Если модуль зависел от других модулей, их перечисляли в массиве зависимостей.

```javascript
// Определение модуля-объекта с данными
define(function() {
  return {
    color: 'black',
    size: 'unisize'
  }
})

// Экспорт функции
define(function() {
  return {
    sum: function(a, b) {
      return a + b
    },
  }
})

// Определение массива зависимостей
define(['path/to/module1', 'path/to/module2'],
function(module1, module2) {
  return {
    someComplicatedLogic: function(arg) {
      return module1.doStuff(module2.doMoreStuff(arg))
    }
  }
})
```

Но, даже несмотря на такую многословность, сейчас в вебе достаточно много легаси, который использует AMD. Уж очень была заманчива идея наконец структурировать код.

_CommonJS_ — это модульная система, которую использует Node.js.

Node.js считает модулем любой файл _.js_.

Для экспорта из модуля используют объект `exports`. Его, как и функцию `require`, Node.js передаёт в каждый модуль сам. Например:

```javascript
// module1.js

function getName(fullname) {
  return fullname.firstName
}

exports.getName = getName
```

Также для экспорта можно использовать `module.exports`:

```javascript
// module2.js
function showName() {
  return 'js'
}

function calc(a) {
  return a * 2
}

module.exports = { showName, calc }
```

`exports` — это ссылка на `module.exports`. Поэтому в `exports` можно добавлять поля, но нельзя присвоить ему новый объект: `exports = { … }` экспорт не изменит. Экспорт через поля `exports` называется именованным.

Для импорта вызывают функцию `require`.

```javascript
// main.js
const { getName } = require('./module1.js')
const { showName, calc } = require('./module2.js')
```

Если модуль экспортирует только одну сущность, можно использовать экспорт по умолчанию. В этом случае при импорте не нужна [деструктуризация](/js/destructuring-assignment/).

```javascript
// person.js
function Person(id) {
  this.id = id
}

Person.prototype.setName = function(name) {
  this.name = name
}

module.exports = Person

// main.js
const Person = require('./person.js')
```

Именованные экспорты и экспорты по умолчанию встречаются и сейчас. Разницу между ними подробнее рассмотрим чуть дальше.

_UMD (Universal Module Definition)_ — универсальная модульная система, совместимая и с AMD, и с CommonJS.

</details>

#### ECMAScript или ES-модули

_ES-модули_ — модульная система на уровне языка, которая появилась в спецификации ES2015. Далее, когда мы будем говорить о модулях, мы будем иметь в виду именно ES-модули.

С 2018 года ES-модули поддерживают все основные браузеры. Node.js работает с ними без флагов с версий 12.17 и 13.2.

С версий 20.19, 22.12 и 23 Node.js умеет подключать ES-модули и через `require()`. Это работает, если ни в модуле, ни в его зависимостях нет [`await`](/js/async-await/) на верхнем уровне, то есть вне асинхронных функций.

В ES-модулях для экспорта используют ключевое слово `export`, а для импорта — `import`. Если поставить `export` перед объявлением функции, переменной или класса, их можно импортировать в другом модуле. Чтобы импортировать сразу несколько имён, перечислите их через запятую.

Чтобы поменять имя при импорте или экспорте, используйте ключевое слово `as`. Экспортировать можно и после объявления: так удобно собрать все экспорты в конце файла.

```javascript
// module1.js

// Экспортированная функция
export function sum(a, b) {
  return a + b
}

// Экспорт констант
export const SOME_SETTINGS_FLAG = false
export const user = {}
export const books = ['Война и мир', 'Мастер и Маргарита']

// module2.js

// Доступ к функциональности из первого модуля
import { sum } from './module1.js'

// Импорт констант
import { books } from './module1.js'

// Изменение имени функции или переменной, которую импортируем
import { user as admin } from './module1.js'

// Изменение имён во множественном импорте
import {
  books as library,
  SOME_SETTINGS_FLAG as turnedOn
} from './module1.js'

// Экспортируем функциональность
const settings = {}
export { settings }

// Изменяем названия при экспорте
const guest = {}
export { guest as visitor }
```

Такие экспорты называются _именованными_. У них обязательно есть имя, и по этому имени другие модули их импортируют.

#### Экспорты по умолчанию

Есть и _экспорты по умолчанию_. Их записывают как `export default`, и имя у экспортируемой функции можно опустить. При импорте такого экспорта фигурные скобки не нужны, а имя можно выбрать любое.

```javascript
// sum.js

// Экспорт безымянной функции по умолчанию
export default function (a, b) {
  return a + b
}

// other-module.js

// Импорт функциональности в другом модуле
import sum from './sum.js'

// Сразу используем другое имя
import superCoolSummator from './sum.js'
```

Многие разработчики считают экспорты по умолчанию менее удачной практикой. Названия именованных экспортов задаёт сам модуль, поэтому во всех импортах они одинаковые. Их легко найти поиском и переименовать средствами рефакторинга. А импорт несуществующего имени сразу даёт ошибку.

Мы рекомендуем использовать именованные экспорты вместо экспортов по умолчанию там, где это возможно.

### Возможности и ограничения модулей

#### Модули — это всегда `use strict`

Модули всегда работают в [строгом режиме](/js/use-strict/). Ещё одно отличие от обычного скрипта: `this` на верхнем уровне модуля — это не `window`, а [`undefined`](/js/undefined/).

Подробнее о `this` — в статье «[Контекст выполнения функций, `this`](/js/function-context/)».

#### Переменные изолированы внутри

Модули не видят «внутренностей» других модулей.

Здесь модуль тоже удобно сравнить с функцией. Доступа к локальным переменным функции ни у кого нет: они доступны только внутри этой функции. Так же и с модулем: его переменные и функции доступны только внутри него. Наружу попадает только то, что модуль явно экспортирует.

Поэтому модули не конфликтуют из-за одинаковых имён. И другому модулю не достанется «что-то лишнее».

Делиться данными между модулями можно и через глобальный объект `globalThis` (в браузере это `window`). Но так не стоит делать: это засоряет глобальную область видимости и может приводить к неожиданным результатам.

#### Код модуля выполняется лишь раз

Код модуля выполняется один раз, при первом импорте. Даже если модуль импортируют несколько других модулей:

```javascript
// module1.js
export const user = { name: 'Alex' }
console.log(user.name)

// module2.js
import { user } from './module1.js'

// module3.js
import { user } from './module1.js'

// main.js
import './module2.js'
import './module3.js'
// 'Alex' выведется в консоль один раз:
// модуль запоминается по адресу и повторно не выполняется
```

Из-за этого все модули получают один и тот же объект, а не копию. Если один модуль удалит поле, то модуль, который выполнится после него, этого поля уже не увидит.

Чтобы этого избежать, создавайте объекты фабрикой. В примере это функция `createUser`. Каждый её вызов возвращает новый объект, поэтому изменения в одном модуле не затронут другие.

```javascript
// module1.js
export const user = { name: 'Alex' }

// module2.js
import { user } from './module1.js'
console.log(user.name)
// 'Alex'

// Удаляем поле
delete user.name

// module3.js, выполняется после module2.js
import { user } from './module1.js'

// Пытаемся вывести удалённое поле
console.log(user.name)
// undefined

// module1.js, фабрика для создания объектов
export function createUser() {
  return { name: 'Alex' }
}

// module2.js
import { createUser } from './module1.js'

// Создаём новый объект…
const user = createUser()

// …и удаляем поле у свежесозданного объекта
delete user.name

// module3.js
import { createUser } from './module1.js'

// …поэтому в третьем модуле поле на месте
const user = createUser()
console.log(user.name)
// 'Alex'
```

#### Особенности в браузере

В браузере модули работают через подключение [скриптов](/html/script/) с атрибутом `type="module"`:

```html
<body>
  <script src="module1.js" type="module"></script>
  <script src="module2.js" type="module"></script>
</body>
```

В браузере у модулей есть свои правила.

**Такие скрипты по умолчанию отложенные**. Загрузка модулей не блокирует отрисовку страницы. Выполняются они после разбора HTML, но до события [`DOMContentLoaded`](/js/event-domcontentloaded/), и порядок выполнения сохраняется. В примере выше сначала выполнится _module1.js_, а потом _module2.js_.

С атрибутом `async` модуль выполнится сразу после загрузки, и порядок не сохранится.

**Внешний модуль** с одним и тем же адресом загрузится и выполнится только один раз, даже если подключить его дважды:

```html
<!-- Загрузится и выполнится -->
<script type="module" src="./user.js"></script>

<!--
  Не станет загружаться и выполняться,
  потому что этот модуль уже подключён выше
-->
<script type="module" src="./user.js"></script>
```

**Модули загружаются по правилам [CORS](/tools/cors/)**. Модуль с другого источника (домена, порта или протокола) загрузится, только если его сервер разрешил это заголовком `Access-Control-Allow-Origin`. По той же причине модули не работают, если открыть _index.html_ с диска: нужен локальный сервер.

**Сервер должен отдавать модули с JavaScript MIME-типом**. Его указывают в заголовке `Content-Type`, например `text/javascript`.

**Путь к файлу указывают явно**. Это полный URL или путь, который начинается с `/`, `./` или `../`. Браузер запрашивает ровно этот адрес: он сам не подставит `.js` и не будет искать _index.js_ в папке.

То есть:

```javascript
// Неправильно
import user from 'user'

// Должен быть или полный URL
import user from 'https://example.com/js/user.js'

// …или относительный
import user from './user.js'
```

Короткие имена вроде `'user'` браузер понимает, только если их описать в карте импортов (_import map_). Это JSON в теге `<script type="importmap">`:

```html
<script type="importmap">
  {
    "imports": {
      "user": "./js/user.js"
    }
  }
</script>

<script type="module">
  import user from 'user'
</script>
```

Ставьте карту выше всех тегов `<script type="module">` на странице. Все основные браузеры поддерживают карты импортов с 2023 года.

#### Динамический импорт

Модуль можно загрузить не сразу, а когда он понадобится. Для этого есть выражение `import()`, похожее на вызов функции. Оно возвращает [промис](/js/promise/), который разрешится объектом с экспортами модуля:

```javascript
button.addEventListener('click', async () => {
  const { sum } = await import('./module1.js')
  console.log(sum(2, 3))
  // 5
})
```

Динамический импорт работает и в обычных скриптах, не только в модулях. Все основные браузеры поддерживают его с 2020 года.

### Модули и сборка

Браузеры понимают модули без сборки, но перед выкладкой в продакшен код часто собирают [сборщиком](/tools/bundlers/). Так делают ради скорости и удобства.

Без сборки браузер загружает модули по цепочке: сначала один файл, потом его импорты, потом их импорты. Каждый уровень импортов — это ещё один круг запросов. Сборщик соединяет модули в бандлы, то есть в один или несколько файлов, и цепочка становится короче. А минификация и удаление неиспользуемого кода уменьшают размер бандлов.

Ещё сборщик:

- подключает пакеты из `node_modules` по коротким именам;
- переводит TypeScript и JSX в обычный JavaScript;
- добавляет хеши в имена файлов для кеширования.

При этом в исходниках код по-прежнему разбит на модули. Сборка меняет только то, что получает браузер.
